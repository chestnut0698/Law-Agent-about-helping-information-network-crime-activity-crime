# 链证智析 技术规划

> 本文只回答一个问题：**怎么把「链证智析」做成 AI 原生智能体，而不是网页工作流。**
>
> 产品背景、场景与答辩表述见《设计方案》。本文按执行先后组织：先定范式与骨架，再补工具与材料管线，最后联调展演。
>
> 智能体搭建思路对齐 [Hello-Agents](https://github.com/datawhalechina/hello-agents)（Datawhale《从零开始构建智能体》）：以 LLM 为大脑、以工具为手脚，用 **ReAct（Thought → Action → Observation）** 驱动任务，而不是用前端按钮串联固定流水线。

## 0. 范式选择：我们做哪一类 Agent

Hello-Agents 把当前 Agent 建设分成两派：

| 类型 | 本质 | 典型形态 | 本项目态度 |
| --- | --- | --- | --- |
| 软件工程 / 流程驱动 | LLM 当数据处理后端，步骤由页面或工作流引擎固定 | Dify / Coze / n8n、八页向导、点「下一步」跑完 | **不做** |
| AI 原生 Agent | LLM 自主理解意图、规划、调工具、根据观察纠错 | ReAct / Plan-and-Solve / Reflection | **采用** |

本项目主范式：**任务级 ReAct 智能体**。

- 用户在任务工作台用自然语言提出分析目标（如「对这三案做跨案碰撞并生成线索」）。
- 智能体自己决定：先看概览、要不要刷新材料、何时碰撞、何时抽时间线、何时生成线索、何时读 chunk。
- 前端只负责会话、材料上传、产物预览与原文回链，**不编排分析步骤**。
- 碰撞、规则命中、OCR、分块等确定性能力做成 **工具**；精确计算与强标识比对不交给模型「口算」。

可选增强（时间允许再加，不阻塞 MVP）：

- **Plan-and-Solve**：复杂任务先产出简短计划再执行（计划仍由模型生成，不是页面状态机）。
- **Reflection**：对线索表述做一次自我校核（越界词、缺引用则重写或降级为待核验）。

明确不做：多租户 SaaS、复杂工作流引擎、多智能体辩论框架、模型微调训练、为「未来可能」预建的 `api/services/repositories` 分层。

## 1. 贯穿原则

1. **智能体主导，工具落地。** 业务主路径是 `用户话术 → TaskAgent → 模型 API → 工具 → 观察 → … → 最终回答`。工具负责确定性计算与落库；模型负责选工具、解释结果、组织待核验表述。
2. **先通 Agent 闭环再提精度。** 优先打通「对话能调工具 → 工具能出产物 → 回答能指回原文」。不准用「准确率不够」阻塞闭环。
3. **证据优先。** 实体、关系、线索须带可定位引用（chunk / 页码）；对不上原文的结果只能标待补证，不进可见线索。
4. **候选与结论分离。** 自动结果默认 `candidate`；合并、采纳由人决定。系统不自动合并实体，不作法律结论。
5. **结构保持扁平可解释。** 沿用现有目录；HTTP 入口在 `app/main.py`，配置在 `app/config.py`，工具在 `tools/`，智能体在 `agents/`。不为工作流再建一层服务编排。
6. **模型调用保持薄封装。** 单模型（默认 DeepSeek `deepseek-v4-flash`）直接走兼容 OpenAI 的客户端即可（类似 Hello-Agents 的 `HelloAgentsLLM`）。超时与简单重试可写在客户端里；**不把「统一网关」当作架构中心**，不为此堆白名单/修复队列/商业级审计。

## 2. 目标架构（AI Native）

```text
用户（自然语言）
    │
    ▼
ui/  任务工作台（会话 + 上传 + 产物预览 + 原文回链）
    │  只调 FastAPI，不编排分析步骤
    ▼
app/main.py + app/tasks.py     # 薄接口：建任务、传消息、推 SSE、读产物
    │
    ▼
agents/task_agent.py           # ReAct 循环（大脑 + 编排）
    │
    ├─► LLM 客户端（DeepSeek / 队友本地 NVIDIA）
    │      Thought / tool_calls / 最终回答
    │
    └─► tools/* + tools_schema.json
           材料：list / status / read_chunk / OCR 修正 …
           任务：overview / collision / timeline / clues …
           法规：search_lawlibrary / search_policy …
           观察写回 messages，供下一轮 Thought
```

与旧「网页工作流」规划的对比：

| 旧安排 | 新安排 |
| --- | --- |
| 八页向导 + service 编排流水线 | 单任务对话 + ReAct 自主调工具 |
| `api → services → repositories` 分层 | 扁平：`main/tasks` + `tools` + `agents` |
| 模型网关为阶段交付物中心 | 薄 LLM 客户端；网关若保留可逐步收薄，非主叙事 |
| 前端点「碰撞」「线索」按钮驱动 | 按钮可保留为快捷话术，真正执行仍由 Agent 调工具 |
| 四个独立「角色智能体」串成流水线 | 一个 TaskAgent；需要时用提示词角色或二次调用，不强制多智能体编排 |

## 3. 技术栈冻结

| 层次 | 选型 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.11+ | 统一 venv |
| 后端 | FastAPI | 入口 `app/main.py`；任务逻辑可在 `app/tasks.py` |
| 智能体 | 自研 ReAct（参考 Hello-Agents 第四章） | `agents/task_agent.py` 为主；遗留 `react_agent.py` 可兼容 |
| 模型 | DeepSeek `deepseek-v4-flash` | 默认；NVIDIA 配置留给队友本地 |
| 工具协议 | OpenAI function calling + `tools_schema.json` | 名称、描述、参数对模型可见 |
| 存储 | SQLite | 任务、材料、chunk、产物、会话 |
| 前端 | 原生 HTML/CSS/JS | 工作台壳，不是流程引擎 |
| 解析 / OCR | PyMuPDF +（页级）OCR | 做成材料工具的前置能力，不是独立「页面阶段」 |
| 图存储 | Neo4j **可选** | 有时间再投影；MVP 可用 SQLite 产物 + 前端展示 |

变更以上关键项时写简短变更说明即可，不必走重流程。

## 4. MVP 必须做到的事

1. 一个监督分析任务内纳入 ≥2 起案件卷宗（PDF / 图 / DOCX / TXT）。
2. 材料可解析为可定位 chunk（页码 / 区间）；质量差的页可提示。
3. 用户用自然语言发起分析；TaskAgent 经 ReAct 调用任务工具完成跨案分析。
4. 强标识确定性碰撞产生「待确认」跨案候选（工具内完成，模型不口算卡号）。
5. 规则线索（如 R001–R005）可生成，并带原文回链。
6. 每条线索可回到材料片段；回答中提示打开产物核验。
7. 输出停留在「疑似关联线索（待核验）」；禁止定罪、并案、主从犯、量刑等表述（提示词 + 简单输出检查即可）。

MVP 不做：完整 RBAC 矩阵、外发审批流、Alembic 全套迁移仪式、强制 Neo4j、商业级模型网关与修复队列。

## 5. 阶段安排（按 Agent 能力推进）

### 阶段 A：Agent 骨架跑通【必须】

**目标**：Hello-Agents 式最小闭环——LLM 客户端 + 工具注册 + ReAct 循环 + 流式输出。

做什么：

1. 薄 LLM 封装：读 `.env` 的 key / base_url / model；支持流式；失败返回明确错误（不必上「网关」叙事）。
2. 工具三要素对齐教程：`name`、自然语言 `description`、可执行函数；集中在 `tools/tools.py` + `tools_schema.json`。
3. `TaskAgent`：`Thought → tool_call → Observation` 循环，有最大轮次，防止死循环。
4. FastAPI：`POST /api/tasks/{task_id}/agent/chat` 以 SSE 吐出思考 / 工具 / 观察 / 最终回答。
5. 前端：任务绑定对话区能看到工具轨迹与最终回答。

**门禁**：对空任务说「先看概览」能调到 `get_task_overview` 并返回观察；无模型 key 时错误可读，不白屏。

### 阶段 B：材料工具可用【必须】

**目标**：卷宗进入 Agent 可读取的世界，而不是另一套「材料中心工作流产品」。

做什么：

1. 上传落库、解析、分块、基础脱敏（强度适中：合成材料为主，不必商业级门控）。
2. Agent 工具：`list_case_materials`、`get_material_status`、`read_material_chunk`、`locate_low_quality_pages` 等。
3. 会话附件与正式材料区分：分析依据以材料管线为准。

**门禁**：Agent 能根据用户问题自行读到指定 chunk，并在回答中引用页码或片段信息。

### 阶段 C：确定性分析工具【必须】

**目标**：把「准」放进工具，把「怎么用」交给 Agent。

做什么：

1. `tools/entities.py`：规则抽取、标准化、强标识碰撞、排除公共号码、部分掩码不参与强碰。
2. 任务工具：`run_task_collision`、`run_task_timeline`、`generate_task_clues`（R001–R005）。
3. 产物落库（实体候选 / 时间线 / 线索），返回 `artifact_id` 供前端预览。
4. 系统提示词写清：优先调这些工具；不要编造标识；线索须提示用户打开产物核验。

**门禁**：用户只说「帮我做跨案分析」，Agent 能自主完成概览 → 碰撞 → 线索（顺序可自调），并产出至少一条可回链线索。

### 阶段 D：语义增强与体验【应该】

1. 法规 / 政策检索工具（已有可沿用）。
2. 弱线索召回（BM25 等）；仅作候选，不单独定高可信线索。
3. 前端：产物预览、原文高亮、快捷提示词（仍是发话给 Agent，不是本地跑流水线）。
4. 可选 Reflection：对最终线索表述做越界词检查。

**门禁**：完整演示路径无需改库；断网或无 key 时至少材料与确定性工具相关说明清晰（可用脚本化兜底回答，非强制 Fake 网关体系）。

### 阶段 E：评测与交付【应该】

1. 用合成 / 授权脱敏样本做端到端演示脚本（自然语言触发，不是点八个页面）。
2. 对照：纯模型读卷 vs Agent+工具；关注误合并、越界表述、回链是否可用。
3. 文档：运行说明、`.env.example`、演示话术；同步《当前项目已有实际成果及其实现细节说明》。

## 6. ReAct 与工具设计要点（对齐 Hello-Agents）

### 6.1 循环

每个时间步：模型根据用户目标与历史 `(Action, Observation)` 生成 Thought 与 Action；工具执行后把 Observation 追加进上下文；直到模型给出最终回答或触及 `TASK_AGENT_MAX_ROUNDS`。

### 6.2 工具描述是一等公民

模型靠 `description` 决定何时调用。任务工具描述应写清：

- 做什么、不做什么（例：碰撞不做同一人认定）；
- 成功时返回里有哪些字段（尤其 `artifact_id`）；
- 失败时常见原因（材料未就绪、案件不足 2 起等）。

### 6.3 什么必须是工具，什么交给模型

| 必须工具（确定性） | 交给模型 |
| --- | --- |
| 卡号 / 手机号校验与等值碰撞 | 理解用户意图、选择工具顺序 |
| 规则 R001–R005 命中 | 总结观察、组织待核验表述 |
| 读 chunk、列材料状态 | 解释差异、提示人工核验点 |
| 产物落库与版本 | 拒绝越界法律结论（配合提示词） |

### 6.4 提示词边界（代码侧再加一层简单检查即可）

禁止：定罪、漏犯漏罪事实认定、并案建议、主从犯、量刑、把相似写成同一人。  
允许：列出共现、差异、原文出处，并标明待核验。

## 7. 目录约定（与现状一致，不扩分层）

```text
仓库根/
├─ app/
│  ├─ main.py          # FastAPI 入口、静态资源、对话与材料相关路由
│  ├─ config.py        # 模型、提示词、轮次等配置
│  └─ tasks.py         # 监督任务、产物、任务工具实现入口
├─ agents/
│  ├─ base_agent.py    # LLM 客户端基础能力（宜保持薄）
│  ├─ task_agent.py    # 任务级 ReAct（主路径）
│  ├─ react_agent.py   # 遗留会话 Agent（兼容）
│  └─ structured_roles.py  # 可选：抽取/表述辅助，非流水线必经站
├─ tools/
│  ├─ tools.py / tools_schema.json
│  ├─ files.py         # 材料管线 + 材料类工具
│  ├─ entities.py      # 抽取、碰撞、规则
│  └─ 法规检索等
├─ ui/                 # 工作台 + 会话，不承载工作流引擎
├─ config/rules|normalization/
├─ data/
└─ docs/
```

说明：

- 现有 `agents/gateway.py` 若仍被引用，可视为历史薄封装；**后续优化方向是收薄或并回 `base_agent`，而不是继续加重网关**。
- 禁止新增 `app/api`、`services`、`repositories`、`schemas` 等分层目录（见项目结构规则）。

## 8. 数据与样本（务实版）

- 展演以**合成卷宗 + 结构贴近真实的困难样本**为主；公开裁判文书只作语料参考，不作跨案真值。
- 有授权脱敏真材更好，但授权不到位不阻塞开发：用合成材料打通 Agent 闭环。
- 金标准若做：规模可小于原「30–50 组」商业规划，优先覆盖强标识正例、同名负例、掩码号码；双人标注可简化为一人标注 + 一人抽检。

## 9. 安全与合规（够用即可）

本项目非商业交付、材料多为合成，原则是**守住输出边界与基本脱敏**，不做检察院级合规平台：

- 外发模型的文本尽量用已脱敏 chunk；日志避免完整证件号 / 卡号。
- 输出侧禁止法律结论表述。
- 不自动合并实体。
- 不在技术规划中把「统一网关 + 外发审批 + 双门控流水线」写成必建项。

## 10. 排期建议（压缩、以 Agent 为里程碑）

| 周 | 焦点 | 里程碑 |
| --- | --- | --- |
| W1 | 阶段 A：ReAct + 概览工具 + SSE 对话 | Agent 能调工具 |
| W2 | 阶段 B：上传解析分块 + 读 chunk 工具 | Agent 能读卷 |
| W3 | 阶段 C：碰撞 / 时间线 / 线索工具 | 自然语言跑出跨案线索 |
| W4 | 阶段 D + 演示话术与文档 | 可展演 |

两人分工建议按 **Agent / 工具** 切，而不是按页面切：一人盯 TaskAgent、提示词、SSE；一人盯 `files` / `entities` 与产物结构；接口以 `tools_schema.json` 为契约。

## 11. 演示脚本（Agent 视角）

约 10–12 分钟，全程以对话驱动：

1. 创建任务，上传案件 A/B（含扫描页），展示材料状态工具结果。
2. 用户：「先看看这个任务有什么材料、能不能分析。」→ Agent 调 overview。
3. 用户：「做强标识碰撞，注意同名不要当成同一人。」→ Agent 调 collision，打开实体候选产物。
4. 用户：「生成跨案线索并标出原文。」→ Agent 调 clues，两次点击回链。
5. 用户：「谁是漏犯？该不该并案？」→ Agent 拒绝并给出合规替代（列共现与出处）。
6. （可选）导入案件 C，用户要求增量分析，展示新产物与旧结果待复核提示。

断网预案：确定性工具仍可被「脚本化助手」或本地说明调用；不把 Fake 网关体系当成交付核心。

## 12. 交付前自检

- [ ] 主路径是 TaskAgent ReAct，而不是前端步骤条。
- [ ] 碰撞 / 规则在工具内完成，模型不编造标识。
- [ ] 线索可回原文；无引用不上主展示。
- [ ] 无自动实体合并；无法律结论输出。
- [ ] 目录仍扁平；无多余分层与占位文件。
- [ ] 单模型薄客户端可运行；网关非架构卖点。
- [ ] 《当前项目已有实际成果及其实现细节说明》与实现一致。
