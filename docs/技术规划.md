# 链证智析 技术规划

> 本文只回答一个问题：**怎么从零把这个智能体做出来。**
>
> 产品背景、应用场景、创新点、答辩表述见《设计方案》，本文不重复。本文按实际执行先后组织，从粗到细，每一阶段给出做什么、怎么做、交付什么、通过什么条件才允许进入下一阶段。

## 阅读方式

**优先级标记**：【必须】= 不做则系统不成立；【应该】= 影响可用性与说服力；【可选】= 时间允许再做，缺失不阻塞验收。

**贯穿全程的五条工程原则**：

1. **先通链路再提精度。** 任何阶段都先让"导入 → 解析 → 抽取 → 碰撞 → 线索 → 回原文"这条路走通，再回头优化每一段的质量。不允许用"准确率还不够"阻塞链路打通。
2. **证据优先。** 实体、关系、角色记载、线索都必须携带 `chunk_id` 级别的证据引用；无法定位原文的结果只能标记为待补证，不进入可见输出。
3. **候选与结论分离。** 自动产生的一切默认是 `candidate`，合并、拆分、采纳由人决定并留痕。系统不自动合并实体。
4. **幂等与增量。** 每个处理步骤都有稳定键，重复执行不产生重复记录；材料或实体变化时只重算受影响范围。
5. **版本化与审计。** 解析器、提示词、规则、词典、索引、评分口径都有版本号；关键动作写审计事件，审计只追加。

**四段节奏**：阶段 0—2 搭骨架，阶段 3—5 打通确定性核心，阶段 6—8 增强与联调，阶段 9—11 验证、交付与排期收口。

## 阶段 0：开工前冻结范围与边界

这一阶段不写业务代码，产出的是一份被两人共同确认的边界文档。目的是避免中途反复改方向。

### 0.1 MVP 范围冻结【必须】

MVP 必须做到的七件事：

1. 在一个案件池内导入 2 起以上案件的卷宗材料（数字 PDF、扫描 PDF、图片、DOCX、TXT）。
2. 解析并形成可定位到页码与字符区间的 chunk。
3. 抽取人员、账户（银行账户/银行卡/支付账户）、电话、设备、网络地址、组织六类核心对象。
4. 对强标识执行确定性跨案碰撞，产生"待确认"的跨案实体候选。
5. 人工确认合并/保持分离后，把结果投影到 Neo4j 并生成跨案关联线索。
6. 每条线索可一键回到原文页面与语句。
7. 输入与输出双重门控生效，越界请求被拒绝，越界表述不外露。

MVP 明确不做：多租户 SaaS 化、并发批量任务调度、复杂工作流引擎、移动端、实时协作编辑、模型微调训练。

### 0.2 技术栈冻结【必须】

| 层次 | 选型 | 约束 |
| --- | --- | --- |
| 语言/运行 | Python 3.11+ | 统一虚拟环境，依赖锁定 |
| 后端 | FastAPI | 复用现有入口，接口只调用服务层，不直接访问存储或模型 |
| 前端 | 原生 HTML / CSS / JavaScript | 复用现有界面与组件，按页面和公共模块拆分 |
| 数据校验 | Pydantic v2 | 所有跨层对象与模型输出都有 Schema |
| 业务存储 | SQLite（WAL、外键开启） | **业务事实源**，唯一写入权威 |
| 图存储 | Neo4j 5.x | **可重建的关系投影**，只存 `chunk_id`，不存正文 |
| 文档解析 | PyMuPDF | 取文本、页码、bbox |
| 扫描识别 | PaddleOCR | 页级触发，保留坐标与置信度 |
| 检索 | BM25 + Embedding 混合 | 只做候选召回与排序增强，不单独定线索 |
| 模型 | DeepSeek V4 Flash | 统一网关访问，结构化输出 |
| 迁移/测试 | Alembic、pytest | 数据变更必须有迁移脚本 |

冻结含义：变更以上任一项，需要写一份变更记录说明原因与影响范围，不能在 Issue 里夹带。

### 0.3 输出边界冻结【必须】

系统输出统一停留在"疑似漏犯漏罪关联线索（待核验）"层级。禁止输出：定罪结论、漏犯漏罪事实认定、并案/分案/移送建议、主从犯判断、量刑建议、证据证明力评价、把相似直接写成同一人。评分只用于排列复核顺序，界面与报告不得出现"犯罪概率""核心犯罪人"一类表述。

这条边界不是提示词约束，而是在阶段 4 的智能体协议与阶段 7 的输出门控中以代码固化。

### 0.4 开工前需确认的配置项【必须】

以下八项在阶段 2 之前必须有明确答案，否则环境无法搭建：DeepSeek 网关地址与出口方式、Embedding 模型（本地优先）、Neo4j 部署方式与备份频率、原始文件保存目录、数据保留期限、报告审批角色、规则发布审批人、金标准脱敏责任人。

**阶段 0 交付**：范围冻结说明、技术栈冻结表、输出边界清单、配置确认表。**门禁**：两人对 MVP 七件事与禁止项无分歧；配置项全部有责任人。

## 阶段 1：数据收集与金标准建设

这一阶段与阶段 2 并行启动，但**必须早于阶段 5 完成第一批可用样本**，否则碰撞规则与阈值无从验证。数据是这个项目最容易被低估的瓶颈。

### 1.1 收集什么【必须】

**规模**：30—50 组，每组 2—3 起相互关联的案件。总案件量约 70—150 起。规模控制在此区间，不机械扩充低价值样本。

**卷宗文书种类**（每组至少覆盖 4 类）：起诉意见书/审查报告、讯问与询问笔录、银行流水与交易明细、微信/QQ 等聊天记录截图、通话详单、扣押清单与电子设备勘验记录、转账凭证与支付平台记录、身份与户籍材料。

**载体形态**：数字 PDF、扫描 PDF、手机截图图片、DOCX、纯文本，五类都要有；扫描件与截图合计不少于三分之一，否则 OCR 链路无法被真实检验。

**关联类型分布**（建议配比）：

- 8—10 组：同银行卡/账户/电话/SIM 卡等**强标识**跨案正例。
- 6—8 组：设备标识、IP、支付账户、地点等**次强标识**正例。
- 6—8 组：角色演变、记载冲突、反向材料、链条断点。
- 4—6 组：**困难正例**——别名与化名、部分掩码号码、格式差异、OCR 错字导致的写法不一致。
- 4—6 组：**困难负例**——同名不同人、公共联系人（客服、律师、办案单位电话）、网吧或共享设备、动态 IP 巧合。
- 4—6 组：完整负例，组内确实不存在跨案关联，用于测量误报。

困难样本是这批数据的核心价值。如果全是"同一张卡出现在两个案子"这样的简单正例，评测结果没有说服力。

### 1.2 从哪里收集【必须】

按合规强度分四档，优先级从高到低：

1. **学校授权的案例库/教学库**：走学校数据使用审批，签数据使用承诺书，明确用途限定为本项目验证、不得外传、项目结束后按约定处理。
2. **检察机关依法授权提供的脱敏材料**：需有书面授权与脱敏交接记录，材料在交付前由提供方或经授权的脱敏责任人完成敏感信息处理，我方不接触未脱敏原件。这是最有价值但周期最长的来源，**第一周就要启动沟通**。
3. **公开裁判文书**：**只能作为语言样本**，用于学习文书表述习惯、句式、称谓、要素写法，为合成材料提供语料参考。
4. **合成材料**：按真实卷宗的结构与表述特征构造，用于补齐第 1、2 档不足的部分，特别是困难样本——真实材料里刻意找"同名不同人 + 部分掩码 + OCR 错字"三者叠加的组合非常困难，合成更可控。

**必须强调**：公开裁判文书**不能替代跨案卷宗真值**。裁判文书是审判后的凝练叙述，已经完成了事实认定与主体归并，不包含卷宗中那些分散的、矛盾的、需要碰撞才能发现的原始记载；用它做金标准，等于把"答案"当成"题目"，会系统性高估发现能力。因此裁判文书不进入金标准的真值标注，只进入语料参考目录。

### 1.3 合规处理【必须】

- 所有真实材料进入仓库前完成脱敏：姓名转化名、身份证号/银行卡号/手机号/地址按规则替换，**替换必须保持一致性**（同一实体在同组内替换为同一化名/同一假号），否则跨案关联的真值会被脱敏本身破坏。
- 脱敏对照表单独存放于仓库之外的受控位置，不进 Git，不进日志，不进模型请求。
- 数据仓库目录写入 `.gitignore`；仓库内只提交标注规范、切分清单与统计脚本，不提交材料本体。
- 每组数据记录来源档、授权凭据编号、脱敏责任人、入库时间。

### 1.4 目录约定【必须】

```text
data/goldens/
├─ manifest.yaml            # 组清单：组号、来源档、案件数、覆盖类型、切分归属
├─ groups/
│  └─ G001/
│     ├─ cases/             # 按案件分目录存放脱敏或合成材料
│     ├─ truth/
│     │  ├─ entities.yaml   # 实体与别名真值
│     │  ├─ links.yaml      # 应合并 / 不应合并 / 应发现的跨案关联
│     │  ├─ evidence.yaml   # 每条真值对应的文件、页码、原句
│     │  └─ negatives.yaml  # 困难负例说明
│     └─ meta.yaml          # 标注人、复核人、分歧裁决、版本
└─ corpus_reference/        # 公开裁判文书语言样本，不参与真值
```

### 1.5 标注规范【必须】

- 每组由**两名**具有法律或办案背景的人员独立标注，互不可见对方结果。
- 标注四件事：应当发现的跨案关联（含理由与依据原文）、不应当发现的关联（困难负例，写明为什么容易误判）、每条关联的原文出处（文件 + 页码 + 原句）、实体别名与不合并说明。
- 分歧由第三人讨论裁决，裁决过程写入 `meta.yaml`，不覆盖原始两份标注。
- 真值只描述"材料记载了什么"和"这两处记载是否指向同一对象"，**不标注是否构成犯罪、是否应当并案**。
- 标注规范本身有版本号；规范变更后已标注数据需重新抽检。

### 1.6 质检与数据切分【必须】

质检：两人一致率低于 80% 的组打回重标；原文出处必须能被脚本按页码定位到（写一个校验脚本自动跑）；每组至少一个困难样本。

切分为三份，**开工时即固定，不允许中途调整**：

- **dev 集**（约 40%）：开发期随便看、随便调参。
- **threshold 集**（约 20%）：只用于阶段 6 末尾冻结阈值，冻结后不再使用。
- **test 集**（约 40%）：**封存**，只在阶段 9 的正式评测中运行一次；若因发现缺陷需重跑，必须记录重跑次数与原因。

**阶段 1 交付**：manifest 与切分清单、标注规范、至少 30 组完成双人标注与裁决、校验脚本。**门禁**：不少于 30 组通过质检；三档切分固定；困难正例与困难负例数量达到 1.1 节配比；脱敏对照表不在仓库内。

## 阶段 2：工程与前后端骨架

目标是**两周内跑通一个空壳系统**：能登录、能建案件池、能上传文件、能看到一个空的线索列表。此阶段不追求任何分析质量。

### 2.1 现状盘点与复用原则【必须】

新系统直接在旧版结构上演进。当前已具备 FastAPI 入口、ReAct 智能体、工具注册、静态前端、会话与文件上传、法规库及基础测试，这些文件保留在原目录：`app/`、`agents/`、`tools/`、`ui/`、`data/`、`knowledge/`、`test/`、`requirements.txt`。

复用原则：现有功能先保持可运行，再逐步替换内部实现；`app/main.py` 继续作为后端入口，`ui/` 继续承载前端，`agents/` 负责模型任务，`tools/` 负责确定性能力，`knowledge/` 保留法规资料。新增能力优先放入对应旧目录的子模块，不另起一套平行架构，也不提前创建空目录。

### 2.2 分层与依赖方向【必须】

```
ui 前端 → app/api 接口 → app/services 业务服务 → app/repositories → SQLite
                               ↓
                    agents → 模型网关 → DeepSeek V4 Flash
                               ↓
                    tools → 解析 / 检索 / 规则 / 图谱 → Neo4j
```

硬性约束：前端只调用 FastAPI 接口；路由只做参数接收与响应转换；service 负责业务流程、权限、幂等与审计；repository 只做持久化；Cypher 只出现在图谱工具或图仓储中，并使用白名单查询与参数绑定；模型调用一律经统一网关。

### 2.3 推荐目录【必须】

以现有目录为主干，只在职责变复杂时增加子目录：

`scripts/` 至少包含：`seed_dev_users.py`、`sync_neo4j.py`、`rebuild_indexes.py`、`evaluate_goldens.py`、`backup_restore_check.py`。

### 2.4 核心数据对象与存储职责【必须】

只列必要对象，字段在实现时按需扩展，不在本文铺表结构。

**SQLite（业务事实源）** 承载六组对象：

1. **权限域**：组织、用户、角色、案件成员。
2. **范围域**：案件池、案件、池成员关系、池版本。
3. **材料域**：文书、文书版本、解析任务、chunk（正文 + 页码 + 字符区间 + bbox + 哈希）、脱敏项、外发审批、模型运行记录。
4. **实体域**：实体提及、统一实体、归一候选、合并与拆分决定、角色事件、关系、关系证据。
5. **线索域**：规则定义与版本、规则运行、规则命中、线索、线索证据、评分分项、复核决定。
6. **留痕域**：报告版本、导出记录、审计事件、流水线运行记录。

**Neo4j（可重建投影）** 只承载：案件节点、文书逻辑节点、统一实体节点、角色事件节点，以及它们之间的关系。每条关系至少带 `evidence_chunk_ids`、`evidence_mode`、`source_version`、`updated_at`。**不保存任何正文、OCR 全文或脱敏前文本。**清空后必须能由 SQLite 已确认记录全量重建——这一点在阶段 5 用脚本验证。

**文件存储**：原始上传文件、OCR 中间图片（可配置清理）、导出报告、检索索引快照、备份包。

**明确禁止**：SQLite 与 Neo4j 双向自由写入；Neo4j 存正文；Embedding 索引作为业务状态来源；模型响应未经 Schema 校验直接落库。

### 2.5 环境搭建步骤【必须】

1. 建虚拟环境，安装依赖，锁定版本；`.env.example` 补齐全部新增配置，真实 `.env` 不进 Git。
2. SQLite 建库并接入 Alembic，开启 WAL 与外键；写第一版迁移（组织/用户/案件/案件池/文书）。
3. 本地起 Neo4j（Docker 单实例即可），执行约束与索引初始化脚本：`Case.case_id`、各实体 `entity_id`、`RoleEvent.event_id` 唯一约束，案件号哈希与事件类型-时间索引。
4. 模型网关先接 **fake gateway**（返回固定结构化响应），真实网关与 fake 遵守同一 Schema，通过配置切换；`DEEPSEEK_EXTERNAL_CALLS_ENABLED` 默认 `false`。
5. 启动健康检查：缺 Neo4j 密码、检索权重之和不为 1、生产环境使用默认密钥，任一情况启动即失败或明确进入降级模式。

### 2.6 页面壳与服务接口先跑通【必须】

建八个空页面并挂上导航：任务与案件池、材料中心、实体复核、线索中心、角色时间线、链条图谱、原文核验、报告与审计。每页先用 fixture 渲染，但**接口签名按最终形态定义**，后续阶段只换实现不改签名。

服务层先落三个可用能力：创建案件池并加入至少 2 个案件（重复加入幂等）、上传文件并落库（记哈希、建版本）、返回空线索列表。

**阶段 2 交付**：可运行骨架、迁移脚本、Neo4j 初始化脚本、fake gateway、八页空壳、`.env.example`。**门禁**：登录与越权拒绝有测试覆盖并写审计；可建池加入 2 案；上传 PDF 落库成功；Neo4j 约束可重复执行不报错；端到端 smoke test 能从登录走到空线索列表。

## 阶段 3：材料处理管线

这一阶段把"文件"变成"可定位、已脱敏、可安全外发的 chunk"。它是后面所有能力的地基，质量问题在这里堵不住，后面全线遭殃。

### 3.1 上传、版本与哈希【必须】

支持 PDF、图片、DOCX、TXT。文件落盘即算 SHA-256；`documents` 与 `document_versions` 分离，替换生成新版本而非覆盖，旧版本 chunk 标记失效但保留（历史引用要能识别失效）。同案内相同哈希进入"重复待决定"，不静默去重。删除为逻辑删除，且执行前展示影响清单。旧版本的外发审批随版本失效。

### 3.2 解析与 OCR【必须】

PyMuPDF 逐页提取文本、页码、bbox。计算页面文本密度，低于阈值的页面判定为扫描页，**页级**送入 PaddleOCR；不整份文档一刀切，混合版面卷宗很常见。OCR 保留每行坐标与置信度，低置信区域打质量标记。

页级失败不影响已成功页面：解析失败最多重试 2 次后转人工检查；OCR 失败按页重试，不重跑成功页。状态至少覆盖 `PARSED`、`OCR_FAILED`、`NEEDS_OCR_REVIEW`。人工修正 OCR 文本生成新版本，下游候选转 `STALE` 并触发增量重算。

### 3.3 分块与定位【必须】

按目标字符数切分并保留重叠（初始 800/120，属可调阈值）。每个 chunk 必须携带：文书版本 ID、页码、块序号、字符起止、bbox、原文哈希、解析器版本、质量标记。

**稳定性要求**：同一输入重复解析，chunk 的 ID 与顺序必须一致（键为 `document_version_id + ordinal + sha256`）。这是原文回链能长期有效的前提，阶段 3 就要写测试保证。

### 3.4 脱敏与模型外发门控【必须】

本地检测器识别身份证号、银行卡号、手机号、姓名、住址、账号等敏感项，记录类型与偏移区间，生成替换后的脱敏文本。原值与替换值的对照关系单独保管，不进入分析载荷、不进入日志、不进入模型请求。界面展示敏感原值需要单独权限。

任何调用外部模型的请求，必须先经过外发门控：检查文本是否已脱敏、是否有有效外发审批、是否只发送完成任务所需的最小片段。未通过则直接拒绝并记录。门控是**代码级强制**，不是调用方自觉——网关入口处校验，绕过网关的调用在代码评审与测试中拦截。

**阶段 3 交付**：解析/OCR/分块/脱敏/门控五个模块与材料中心页面的处理状态展示。**门禁**：数字 PDF、扫描 PDF、图片、混合版面各有样本通过；重复解析 chunk 稳定；六类敏感项检出有测试；未脱敏文本无法外发（用例验证被拒）；损坏文件、加密文件、超大文件返回稳定错误码而非崩溃。

## 阶段 4：智能体与模型网关

### 4.1 统一网关【必须】

所有模型调用走一个 `agents/gateway.py`，统一走 DeepSeek V4 Flash。网关职责：注入模型名与参数、携带 `purpose`（用途）、`prompt_version`、`input_hash`、审批 ID；写 `model_runs` 记录（含用量、耗时、状态，**不写原文**）；执行超时与重试；提供 fake 实现供测试。模型名只能来自网关白名单。

### 4.2 角色职责划分【必须】

不做花哨的多智能体编排，只设四个职责明确的角色，每个角色输入输出都是结构化对象：

| 角色 | 输入 | 输出 | 边界 |
| --- | --- | --- | --- |
| 抽取智能体 | 脱敏 chunk | 实体/行为/角色事件候选 + 原文引用 | 只抽材料写了的，不推理不补全 |
| 归一说明智能体 | 两个实体的属性与出处 | 一致项、差异项、需人工核对的问题 | **不给出是否同一人的结论** |
| 线索表述智能体 | 已成立的规则命中与证据 | 受控模板下的线索标题与摘要 | 不新增事实、不新增引用 |
| 输出校核智能体 | 待发布线索全文 | 是否越界、是否把候选写成事实、是否遗漏反向材料 | 独立运行，只判定不改写 |

### 4.3 结构化输出、重试与降级【必须】

每个角色对应一个 Pydantic Schema，模型响应先校验再落库。核心不变量：抽取出的每个对象至少一条证据引用；引用的原句必须能在对应 chunk 中反向匹配（比对 `quote_hash`），匹配不上的判为无效候选；`confidence` 限定 0—1 且只用于排序。校验失败的响应进入修复队列，不重试盲刷。

超时与 429 走指数退避加抖动，最多 3 次；返回内容不符合 Schema 属逻辑错误，不重试，进修复队列；外部调用被禁用或网关不可达时，系统降级为"仅确定性规则"模式继续可用，界面明示当前处于降级状态。每次调用写审计，日志中不得出现原始身份证号、卡号、手机号或完整正文。

### 4.4 禁止直接下定论【必须】

所有提示词中写死边界，并在输出侧用规则复核：模型不得输出"是同一人""构成犯罪""应当并案""系主犯""建议量刑"等表述。归一说明智能体只描述异同，判定权在人。这条在阶段 7 的输出门控再做一次独立检查，属于双保险。

**阶段 4 交付**：网关、四个角色的 Schema 与提示词（带版本）、修复队列、降级路径。**门禁**：fake 与真实网关 Schema 一致；超时/429/非法 JSON/Schema 失败四种情况各有测试；关闭外部调用后系统仍可运行；无任何模块绕过网关；敏感日志扫描通过。

## 阶段 5：核心功能第一版（先做确定性）

这一阶段的唯一目标：**在完全不依赖语义相似的前提下，产出第一条可回原文核验的跨案线索。**做完这一阶段，系统已经可以演示。

### 5.1 实体抽取与标准化【必须】

对六类核心对象（人员、账户〔银行账户/银行卡/支付账户〕、电话/SIM、设备、IP/网络地址、组织）做抽取。实现上采用"规则优先 + 模型补充"：卡号、手机号、身份证号、IMEI、IP 这类有明确格式的，用正则与校验位规则抽取，准确且零成本；人员、组织、行为描述交给抽取智能体。两条来源都写入实体提及表，标注 producer 类型。

标准化只做**可逆、可解释**的规范化：去空格与分隔符、全角转半角、常见 OCR 混淆字符标注（0/O、1/l、8/B 不直接替换，而是生成"可能等价"的候选形式）、手机号去区号前缀、账号去掩码星号并记录掩码位置。标准化结果与原始 surface 同时保留，不允许标准化覆盖原文。

标准化词典（银行简称、平台别名、地区简称）放在 `config/normalization/` 并带版本号，词典更新触发受影响候选重算。

### 5.2 强标识碰撞【必须】

在案件池版本范围内，对完整且通过校验的强标识（完整卡号、完整手机号、身份证号、稳定设备标识）做确定性等值碰撞。命中条件：同一规范化值出现在 ≥2 个案件，且每个案件至少有一条有效 chunk 证据。

排除项必须一开始就做，否则误报会淹没结果：公共服务号码（客服、办案机关、律所）、公开收款账户、明显的测试或示例数据、已被人工确认为误识别的值。排除名单放在 `config/rules/` 并可维护。

**部分掩码的号码不参与强碰撞**，只能进入阶段 6 的弱线索候选。

### 5.3 候选的人工合并与拆分【必须】

碰撞产生的是 `NormalizationCandidate`，状态一律 `PENDING`。界面展示：一致项、差异项、冲突字段、各自出现的案件与原文并列。人工动作四种：合并、保持分离、修正、暂缓。

工程要点：命令携带 `expected_version`，防并发覆盖；执行前展示影响范围（涉及多少关系、多少线索）；决定只追加不删除，新旧统一实体用 `supersedes_id` 串联；被人工驳回的候选不得因相同输入重复出现；拆分时旧图节点退役、新实体重新投影。

**"错误自动合并次数 = 0" 是硬指标**，实现上通过"系统不提供自动合并入口"来保证。

### 5.4 Neo4j 同步【必须】

采用 outbox 模式：SQLite 事务内写业务记录与 outbox 事件，异步消费者读取 outbox 投影到 Neo4j。写入用 `MERGE` + 稳定业务 ID，同一事件重复消费不产生重复关系。Neo4j 不可用时 SQLite 写入照常成功，同步进入待重试队列，界面提示图谱数据滞后。

写 `scripts/sync_neo4j.py` 支持全量重建，并写一个一致性检查：清空 Neo4j 后重建，节点与关系数量、版本必须与 SQLite 一致。

### 5.5 基础关系规则【必须】

第一版实现 5 条确定性规则，每条都有 YAML 定义与版本号，命中结果保留可解释的触发依据：

- **R001 同一银行账户/卡跨案出现**——输出关联案件、持有人候选、使用事件、逐案证据。
- **R002 同一手机号跨案出现**——排除公共号码。
- **R003 同一设备标识跨案出现**——排除网吧与共享设备。
- **R004 资金路径交叉**——不同案件的账户在限定跳数（默认 3）与时间窗内发生转账交叉，输出路径、金额区间、时间与逐边证据。
- **R005 共同联系人**——同一联系人与多个案件中的不同主体存在明确联络事件；仅姓名相似不算。

规则区分三种证据模式：`DIRECT_MATERIAL`（材料直接记载）、`RULE_INFERRED`（规则推断）、`HUMAN_ADDED`（人工补充）。共现关系不得升级为控制关系或共同犯罪关系。

### 5.6 线索卡与原文回链【必须】

线索生成器聚合规则命中与证据，产出线索卡：类型、标题（受控模板）、涉及案件与对象、生成方式、支持材料、不确定性说明、固定的法律边界声明。**每条线索至少关联 2 个案件和 2 条有效 chunk**；单案发现另设"观察项"，不冒充跨案线索。

原文回链：从线索、实体、关系任一处两次点击内打开文书页面并高亮语句，同时展示材料名称、类型、版本、页码；扫描页并列展示页面图像与 OCR 文本。打开时校验 `quote_hash`，不一致则明确提示引用失效，禁止悄悄展示旧内容。

**阶段 5 交付**：抽取、标准化、碰撞、人工裁决、图同步、5 条规则、线索卡、原文核验页。**门禁**：在 dev 集上端到端产出至少一条跨案线索并逐项回原文；六类实体抽取有正反样本测试；同名不同人样本保持分离；5 条规则各有正例、近似反例、边界例与幂等测试；Neo4j 清空后可完整重建；**不依赖 Embedding 即可完成完整演示**。

## 阶段 6：核心功能第二版（扩召回、加维度）

第一版解决"准不准"，第二版解决"全不全"和"看不看得懂"。

### 6.1 BM25 + Embedding 弱线索候选【必须】

建立 chunk 级混合索引，检索结果必须受案件池版本与权限过滤。BM25 负责别名、错字、部分号码的字面召回；Embedding 负责行为描述与语义相近表述的召回。融合分同时返回 BM25 分、向量分与融合权重，命中原因可展示。

**边界**：弱线索只产生"待核验候选"，不能单独形成高可信线索；仅有 Embedding 命中的线索总分设上限，默认不进入主列表。Embedding 可整体关闭，关闭后系统功能不缺失。

### 6.2 角色时间线【必须】

按统一实体聚合跨案角色事件，按时间排列。时间精度枚举 `EXACT / DAY / MONTH / RANGE / UNKNOWN`，**未知时间不补造**，单独归入"时间不明"分组。区分材料明确记载、系统推测、人工确认三种来源。存在冲突记载时并列展示，不自动择一。角色词表只用于规范展示，不对应任何法律地位。

### 6.3 链条图谱【必须】

从 Neo4j 查询受权限约束的子图。默认展开 2 跳，最大 4 跳，结果默认限制 200 行。查询必须绑定组织与案件池版本，走白名单查询名，页面不提供原始 Cypher 入口。三种证据模式在颜色与文字上双重区分。点击边打开来源侧栏并可跳原文。高度数的公共节点（如客服电话）在路径计算中降权，避免造出虚假链条。

### 6.4 线索评分与去重【必须】

评分是**可解释的加权求和**，不是模型打分。初始维度与权重：规则强度 30、跨案数量 15、标识可靠性 20、证据完整性 20、时间一致性 10、语义支持 5；冲突与证据缺失作为扣分项。总分必须能由分项重算复现，界面展示分项。

硬约束：无跨案证据总分上限 39；仅 Embedding 命中总分上限 39；无有效原文回链直接被输出门控阻断；存在强标识冲突至少扣 30 分并强制人工复核；人工不能直接改总分，只能修改事实状态后触发重算。

去重用 fingerprint（规范化主体集合 + 案件集合 + 线索类型 + 规则集合的哈希），同 fingerprint 更新同一条线索的新版本而非新增。

### 6.5 冲突与反向材料【必须】

线索卡必须有"反向材料"区。生成线索时主动检索与结论方向相反的记载（如另一案件称该账户由他人控制），一并列出。遗漏反向材料属于输出门控的检查项之一。矛盾记载并列展示，系统不择一。

### 6.6 增量更新【必须】

触发源：新增文书、替换文书、删除文书、实体合并、实体拆分、规则更新、词典更新、模型或提示词升级。

处理原则：先算影响清单并展示，高影响操作由用户确认后执行；只重算受影响范围，未受影响的既有结果与人工判断保持不变；受影响的旧结论转 `PENDING_REVIEW` 或 `STALE` 并说明变化原因；模型升级不覆盖历史结果，创建新的 pipeline 版本；人工已确认的线索不被后台任务静默降级。

**阶段 6 交付**：混合检索、时间线、图谱、评分与去重、反向材料、增量引擎。**门禁**：BM25 与 Embedding 可分别开关且融合可解释；评分分项可展示且可复现；图谱与时间线在 dev 集上可用；新增一份材料只重算受影响部分并有影响清单；阈值在 threshold 集上完成冻结（见附录 B）。

## 阶段 7：安全与人工复核

安全能力从阶段 2 就开始埋点，这一阶段做集中加固与验证。

### 7.1 输入与输出双门控【必须】

**输入门控**在调用任何分析能力前判定 `ALLOW / CLARIFY / DENY`。拒绝类型：权限不足、授权过期、案件超出池范围、目的不明、提示词注入、以及请求内容属于禁止事项（判断谁是漏犯、是否并案、是否构成犯罪、主从犯、量刑）。被拒绝时给出合规替代方式（例如"可以为你列出该账户在池内各案的出现记录与原文"），并写安全事件。

**输出门控**做两道独立检查，顺序不可颠倒：

1. **确定性来源校核**：每项结论是否有证据引用、引用的 chunk 是否存在且未失效、`quote_hash` 是否一致、是否超出授权范围、是否包含敏感原值。
2. **独立语义校核**：表述是否越界、是否把候选写成事实、是否遗漏反向材料。校核角色只判定不改写，不得补写事实。

任一未通过，结果进入隔离队列，不进入用户可见范围与导出，并记为安全事件。

### 7.2 权限、脱敏与审计【必须】

权限按组织、角色、案件成员、案件池成员、操作类型联合判定，判定发生在服务端边界而非页面。查看原值、确认合并、处置线索、导出报告分别授权。审计覆盖登录、授权变更、材料操作、模型调用、实体处置、线索复核、报告导出，记录只追加不可修改，且不含敏感原值。

### 7.3 状态流转与复核闭环【必须】

线索状态使用受控枚举：`PENDING_REVIEW / FOLLOW_UP / NEED_MORE_MATERIAL / DISMISSED / DEFERRED / CLOSED / REOPENED`。处置必填理由；关键线索支持双人复核；关闭后出现新材料可重开。状态是工作流状态，**不得被表述为事实认定或法律结论**。

### 7.4 报告【应该】

报告绑定组织、任务、案件池版本、文书版本、实体版本、规则版本、模型与提示词版本、索引版本与文件哈希。只包含当前有效且已通过门控的内容；固定边界声明不可移除；重复导出生成新版本；已发布报告不可删除，只能撤回。

**阶段 7 交付**：双门控、权限矩阵、审计查询、复核闭环、报告生成。**门禁**：越界请求拦截率在测试矩阵上无漏出；未脱敏材料外发被阻止；含失效引用或越界表述的线索无法展示与导出；越权访问矩阵全部拒绝并留痕。

## 阶段 8：前端完善与联调

前面各阶段页面只做到"能用"，这一阶段做到"好用且可演示"。每页给出明确验收条件。

| 页面 | 核心内容 | 验收条件 |
| --- | --- | --- |
| 案件池/任务 | 池列表、案件构成、授权状态、待办统计 | 少于 2 案不能发起分析；移出前展示影响 |
| 材料中心 | 清单、处理状态、质量提示、版本、预览 | 每份材料状态与失败原因可见；可发起重解析 |
| 实体复核 | 候选列表、差异对比、原文并列、合并/拆分、影响预览 | 高风险动作二次确认；并发冲突有提示；取消不改数据 |
| 线索中心 | 筛选、线索详情、依据链、反向材料、处置 | 每条线索两次点击内到原文；处置理由必填 |

**门禁**：八页验收条件全部通过；一次完整演示路径无需手工改库即可跑完。

## 阶段 9：测试与评测

### 9.1 测试金字塔【必须】

- **单元测试**（约 60%）：标准化、指纹、评分、规则、门控、状态机；每条规则至少 1 正例 + 2 反例 + 1 边界例；不依赖真实模型。
- **契约测试**：Pydantic Schema、网关（fake 与真实同 Schema）、图仓储返回结构、FastAPI 接口契约；证据引用完整性作为通用契约。
- **集成测试**：迁移与事务、PyMuPDF + PaddleOCR 混合解析、outbox → Neo4j 投影、索引更新。
- **E2E**（约 10%）：四条路径——建池导两案出线索并回原文；候选合并/驳回后图同步与线索重算；新增材料触发增量与报告新版本；双门控阻断。
- **安全测试**：RBAC 越权矩阵、提示词注入、结构化输出污染、Cypher 注入与超深查询、恶意文件与路径穿越、敏感日志扫描、备份恢复与中断恢复。

### 9.2 三组对照实验【必须】

三组严格统一使用同一批封存 test 集（约占全部 30—50 组数据的 40%，每组 2—3 案）、同一评价口径、同一评测脚本版本：

- **第一组：直接 DeepSeek。** 把同组脱敏材料直接交给 DeepSeek V4 Flash，要求给出跨案关联线索，不做结构化抽取、不做碰撞、不给图谱。用于建立基线，观察无依据补充、身份误合并、定位偏差与越界结论。
- **第二组：DeepSeek + 结构化碰撞。** 先做结构化抽取，再对强标识执行确定性碰撞，弱线索做候选召回，但不引入图谱、时序与人工闭环。用于隔离结构化处理带来的增益。
- **第三组：完整工作流。** 解析/OCR → 抽取校验 → 归一与人工裁决 → 图谱投影 → 混合召回 → 角色与链条分析 → 双门控 → 人工复核 → 增量更新。用于验证端到端的发现能力、可核验性、安全性与人工成本。

评测指标按《设计方案》第十章的业务口径落到脚本：发现率、有效线索占比、误报率、错误自动合并次数（要求 0）、回链可用率（要求 100%）、越界拦截漏出（要求 0）、单条线索平均核验耗时、增量相对全量的耗时下降。结果按分布呈现，不只报均值。

### 9.3 失败案例【必须】

每轮评测必须产出失败案例集，至少覆盖：同名不同人误召回、掩码号码假碰撞、动态 IP 误连、OCR 错字错配、行为被误标为角色、时间缺失导致的错误演变、公共节点造成的虚假链条、反向材料遗漏、材料替换后引用失效、模型越界表述。每例说明输入特征、系统表现、本应生效的机制、是否被门控或人工发现、修正措施与修正后结果。失败案例进版本库，不隐藏。

**阶段 9 门禁**：三组对照完整执行且干净环境可复现（容差内）；硬指标（错误自动合并 0、回链 100%、越界漏出 0）达标或有书面风险接受；安全测试全部通过；失败案例集完成。

## 附录 A：关联算法主流程

```
chunk（已脱敏、可定位）
  │
  ├─[1] 抽取：正则/校验位规则 + 抽取智能体 → 实体提及（带证据）
  │
  ├─[2] 标准化：格式归一 + 词典映射 → 规范值（保留原始 surface）
  ├─[3] 强标识碰撞（确定性）：完整卡号 / 手机号 / 身份证号 / 稳定设备号
  │      条件：同一规范值 ≥2 案件 且 每案 ≥1 有效 chunk
  │      过滤：公共号码、公开账户、共享设备、测试数据
  │      → 高可信候选（仍为 PENDING）
  ├─[4] 弱标识候选（扩召回，不定论）：姓名与别名、部分掩码号码、
  │      OCR 近似形、BM25 字面召回、Embedding 语义召回
  │      → 低可信候选（标注召回原因与相似度，单独分组）
  ├─[5] 人工确认（唯一的合并决定点）
  │      展示一致项 / 差异项 / 冲突字段 / 各自原文
  │      动作：合并 / 保持分离 / 修正 / 暂缓（必填理由，写审计）
  │      → 统一实体（带版本与 supersedes 链）
  ├─[6] 图投影 → Neo4j（outbox 幂等，只带 chunk_id）
  ├─[7] 规则命中 + 有限跳数路径发现 → 关系与路径（区分三种证据模式）
  ├─[8] 线索生成：聚合 → 反向材料检索 → 评分（可解释分项）→ fingerprint 去重
  └─[9] 输出门控（来源校核 → 独立语义校核）→ 线索中心 → 人工复核 → 报告
```

三条不可违反的顺序约束：弱标识永远不能跳过第 5 步直接成为关系；第 3 步的排除过滤必须在候选生成前执行；第 9 步失败的内容不进入任何用户可见界面。

## 附录 B：关键阈值与冻结方式

以下参数**一律不拍脑袋定**。做法是：阶段 3—6 期间用 dev 集调试取初值；阶段 6 末在 threshold 集上做一次网格或逐项扫描，选定后写入 `config/` 并标注冻结日期与依据；test 集只在阶段 9 使用一次，不用于调参。

| 阈值 | 初值 | 影响 | 冻结依据 |
| --- | --- | --- | --- |
| OCR 触发文本密度 | 0.08 | 漏 OCR / 无谓 OCR | 扫描页识别率与耗时 |
| chunk 长度 / 重叠 | 800 / 120 字符 | 定位精度与召回 | 原文回链准确率 |
| BM25 / Embedding 权重 | 0.65 / 0.35 | 召回构成 | threshold 集 Recall@K 与误报增量 |
| 弱线索候选相似度下限 | 待定 | 候选数量与人工负担 | 人工可承受候选量与漏检率的折中 |
| 线索进入主列表分数线 | 40 | 列表噪声 | 有效线索占比 |
| 图路径最大跳数 | 默认 2 / 上限 4 | 虚假链条风险 | 虚假路径比例 |
| 公共节点降权度数 | 待定 | 虚假链条风险 | 困难负例组表现 |
| 模型重试次数 | 3 | 稳定性与成本 | 失败率与耗时 |

冻结后若必须调整，需重跑 threshold 集并记录调整原因，不得在评测中途改参。

## 附录 C：幂等键与增量失效

**稳定键**（重复执行先查键，命中即返回既有结果）：文书版本 `document_id + version_no`；chunk `document_version_id + ordinal + sha256`；模型运行 `purpose + prompt_version + input_hash`；抽取候选 `chunk_id + extractor_version + payload_hash`；图投影 `aggregate_type + aggregate_id + aggregate_version`；规则运行 `pool_id + rule_version_set + input_fingerprint`；线索为规范化主体集合、案件集合、线索类型与规则集合的哈希。

**增量失效规则**：

| 变化 | 重算范围 |
| --- | --- |
| 新增文书 | 该文书 + 所属案件池内与其新增标识相关的候选 |
| 替换文书 | 旧版本 chunk 失效，其派生候选、关系、线索进入重算 |
| 删除文书 | 先出影响清单，人工确认后执行 |
| 实体合并/拆分 | 重投影涉及实体及其关系、规则命中、线索 |
| 规则更新 | 只重跑使用该规则集的案件池 |
| 词典更新 | 重算被该词典命中的候选 |
| 模型/提示词升级 | 不覆盖历史，创建新 pipeline 版本 |

状态转换使用乐观版本号；人工已确认的结论不被后台任务静默改写，只能转为"待复核"并说明原因。

## 附录 D：交付前逐条自检
